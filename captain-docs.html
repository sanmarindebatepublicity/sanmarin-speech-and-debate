Technical Manual

Instructions for captains and officers who maintain the San Marin Speech & Debate member portal. Everything below assumes you have GitHub repository access.

What to Edit, and Where

Almost everything that changes during a season lives outside the code. Find your row below, and only open GitHub if the row says to.

Sign in with the debate publicity Google account
Every external service this site reads — the Google Form, the Drive photo folder, the shared Drive documents, the team calendar — is owned by the debate publicity Google account. Use that account, not your personal one, or you will be locked out of things the site depends on. Ask an outgoing officer for the login.
  1. Announcements — edit data/announcements.json
    On GitHub, open data/announcements.json and add an object to the top of the list. Newest first. Each entry needs a date, a title, and a body. The optional link and linkText add a button under the announcement — this is how you point people at a Drive folder.
    {
  "date": "2026-09-08",
  "title": "Quarry Lane packet is up",
  "body": "Cases, blocks and the prep doc are in the folder.",
  "link": "https://drive.google.com/drive/folders/YOUR_FOLDER_ID",
  "linkText": "Open the tournament folder"
}
  2. Linking a Drive folder from an announcement
    Put tournament packets, practice pieces and prep docs in a folder on the publicity account's Drive. Open the folder, press Share, set General access to Anyone with the link → Viewer, then copy the link into the link field above. If you skip the sharing step the link opens a permission-request screen for everyone but you, which is the single most common mistake here. Always test the link in a private window before you consider it done.
  3. Photos — no code at all
    Drop images into the team's Drive photo folder and they appear on the Media page within about a minute, newest first. To caption one, right-click it in Drive → File information → Description, and type the caption there. It shows under the photo when someone opens it. Nothing in this repository needs editing to add, caption or remove a photo.
  4. Awards — no code at all
    Add a row to the Team Awards database in Notion. It appears on the Team Hub within five minutes. Use the dropdowns for Year and Place rather than typing custom values, so the tags stay consistent.
  5. Sponsors — edit data/sponsors.json
    Same shape as announcements: open the file on GitHub, edit the list, commit.
  6. Lessons and quizzes — edit vault-curriculum.js
    All Training Vault lesson text, quizzes and exercises live in this one file. It is long; use your browser's find to jump to the lesson title you want. Edit the text in place and commit — the Training Vault reads it directly, so there is nothing else to update.
  7. Commit & push
    For any file above, commit with a short message describing the change, for example "announcements: Quarry Lane packet". The site rebuilds and the change is live within a minute or two.

Keeping the Site Alive

A site that has not changed in two months reads as abandoned, and members stop checking it. The habit matters more than the polish.

Post a tip every other Tuesday afternoon. Tuesday afternoon lands after school while the week is still ahead, and every other week is a pace you can actually keep once tournament season starts. Keep each one short — one idea a novice can use at the next practice. A refutation pattern, a flowing shortcut, one thing judges keep writing on ballots. These go in data/announcements.json like any other announcement.

Post the packet before the tournament, not after. Put the folder up as soon as the resolution drops, and link it from an announcement. That is the moment people are looking for it.

Getting Help from an AI Assistant

You do not need to know how this site is built to change it safely. Paste one of the prompts below into an AI assistant such as Claude, along with the file you are looking at, and work from what it tells you. Keep two rules: change one thing at a time, and check the page in a browser before you commit.

1. Understand the site before touching it

This is a plain HTML/CSS/JS website with no build step, deployed on
Vercel. Read the repository and explain how it fits together: which
pages exist, how the member portal login works, and which files I would
edit to change content rather than layout. Do not change anything yet.

2. Change something specific

I want to [describe the change in plain English]. Before editing,
tell me which files you would change and why, and warn me if the same
content is duplicated anywhere else that would also need updating.
Then make the change and tell me how to check it in the browser.

3. Something broke

On [page], [what you expected] but instead [what actually happens].
Find the cause before proposing a fix — check the browser console and
the network tab, and tell me what the actual error is. Do not guess.
When you have the cause, explain it in plain English, then fix it.

4. Check my work before it goes live

Review my uncommitted changes. Check for broken links, content I
changed in one place but not another, anything that would look wrong on
a phone, and any password, API key or private link I have accidentally
included. List problems in priority order. Do not fix anything yet.
Never paste a key or password into a chat
The site's private values — the Google service account, the Notion token — live in Vercel's Environment Variables and in a local .env file that is deliberately never committed. If an assistant asks for one, it does not need it. Nothing on this page requires you to share a credential.

Rotating Access Codes

The portal accepts two codes — one for general members and one for captains. The codes themselves are not stored anywhere in the site's source; only their SHA-256 hashes live in portal.html, in the ACCESS_CODE_HASHES map:

const ACCESS_CODE_HASHES = {
  '<sha-256 hash of member code>':  { role: 'member',  redirect: 'portal-team-hub.html' },
  '<sha-256 hash of captain code>': { role: 'captain', redirect: 'portal-team-hub.html' }
};

To rotate a code: pick the new code, open the browser console on any page of the site (F12 → Console), and run the line below with your new code. Copy the 64-character result and replace the matching hash key in portal.html.

crypto.subtle.digest('SHA-256', new TextEncoder().encode('NEW-CODE-HERE'))
  .then(b => console.log([...new Uint8Array(b)].map(x => x.toString(16).padStart(2,'0')).join('')));
This is still gate UX, not real auth
The site is static, so the gate runs in the visitor's browser and the member pages are technically reachable without it by anyone determined. Hashing keeps the codes out of the page source, but treat the portal as a courtesy gate: rotate codes each season, share them privately (never in a public post), and never put truly sensitive information behind it.

Troubleshooting

A member says their code doesn't work. Confirm they're typing the current season's code exactly — it's case-sensitive. Ask them to clear site data for the portal and retry.

Someone is stuck on a redirect loop. That usually means localStorage is disabled or blocked. Ask them to use a standard Chrome/Safari/Firefox window (not incognito with storage blocked).

I need to sign someone out remotely. You can't — the session is in their browser's localStorage. You can, however, rotate the access code, which instantly invalidates anyone who would try to log in fresh.
